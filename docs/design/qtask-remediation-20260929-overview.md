# qtask_list 全代码评审修复设计

- 日期：2026-09-29
- 状态：实施依据
- 对应计划：`docs/dev/PLAN-020-review-remediation.md`

## 1. 目标与边界

面向长期运行的多队列采集任务，修复执行租约、外存生命周期、管理控制面和观察面之间的契约断点。继续保持 at-least-once：业务处理器需要幂等；库负责不丢消息、状态可审计、危险操作显式。

本设计只支持 standalone/Sentinel Redis。跨 Redis 与外存服务不存在共同事务，因此外存清理使用可重试的补偿队列，不能声称 exactly-once。

## 2. Worker 心跳与租约

### 方案比较

| 方案 | 优点 | 代价与风险 |
|---|---|---|
| 在现有维护循环加超时 | 改动少 | SQLite/网络调用难以可靠中断，仍可能阻塞心跳 |
| 独立心跳与租约线程 | 生命周期清晰，慢维护互不影响 | 多一条轻量线程，需仔细处理 drain 和退出顺序 |
| 外置独立心跳进程 | 隔离最彻底 | 部署和进程协调复杂，不适合库的默认模式 |

采用独立线程。claim 在原子 `begin_attempt` 成功后立即进入待续租集合；线程池待执行和正在运行的 claim 均续租。handler 结束后才移出。Worker drain 期间持续心跳，所有 handler 退出后再清理 worker key。维护线程只做低频检查、归档和告警。

外存下载可能发生在 `begin_attempt` 与 handler 之间，因此先注册临时 claim，再解码 payload；下载失败的状态转换完成后移除临时 claim。Worker 同时把 ID 登记到 `qtask:workers:{queue}`，供总览直接查询。

## 3. RemoteStorage 安全与生命周期

### 3.1 对象所有权方案比较

| 方案 | 优点 | 代价与风险 |
|---|---|---|
| 共享内容键 + 跨系统引用计数 | 节省重复内容空间 | 上传先于 Redis 入队，引用提交和删除存在多个竞态窗口；需要复杂的两阶段协调 |
| 每个任务独占对象 + Redis 清理日志 | 所有权明确，重复入队失败可安全清理；终态回收可重试 | 相同内容会占额外磁盘；人工 replay 需要复制对象 |
| 仅设置固定 TTL | 实现简单 | 无界 live/DLQ 会提前丢 payload；永久 TTL 又无法回收 |

采用任务独占对象。新上传返回随机对象 key，描述符标记 `dedicated=true`。旧内容寻址对象仍可读取，但不得由单个任务的拒绝、完成或删除路径直接删除。人工 replay 对 external payload 创建新对象，给新 task_id 独立生命周期。

### 3.2 保留与清理契约

1. 新任务从上传到 live/在 DLQ 期间持续保留外存对象；deadline 不是外存清理截止时间。
2. 任务进入不再有 operational message 的终态时，同一个 Redis Lua 转换写入外存清理日志，清理时刻为终态 `finished_at + ttl_days`。这保留 skipped/cancelled 的历史重放窗口。
3. 重放先复制对象，再原子创建新任务；旧对象按原任务终态保留期进入清理日志，新对象独立保留。
4. 管理清空/删除遵守同一清理日志；对活跃 processing 的删除先拒绝或要求显式强制取消，不能暗中丢掉审计。
5. 外存清理消费者对每项先确认独占标记，然后删除；网络失败保留日志重试。存储服务自身也可消费同一 Redis 日志，避免最后一个 Worker 停止后永不清理。
6. 上传成功但 Redis 入队失败时，只删除该请求新建的独占对象。旧共享内容键不做即时删除。
7. 上传时先写 24 小时宽限的待入队回收记录；入队/重放成功在同一 Redis Lua 转换中移除。进程在上传后、入队前退出时，该记录可清理孤儿对象；回收消费者抢占待入队对象时，入队脚本拒绝失效引用。

### 3.3 访问控制

服务端默认监听 `127.0.0.1`。配置 `QTASK_STORAGE_TOKEN` 后，所有存储接口使用 Bearer token；未配置 token 时仅允许 loopback 客户端访问。客户端支持显式 token 或环境变量。上传最大体积由配置定义，并在读取完整文件前拒绝超限。

Dashboard 健康接口只展示 Redis 主机与端口，不展示用户、密码和查询参数。CLI 启动日志同样脱敏。

## 4. 管理操作

`delete_task` 和 `clear_queue` 统一通过原子取消脚本移动 operational message、写终态和清理日志。默认拒绝删除活跃 Worker 的 processing；若提供显式强制选项，返回“handler 可能继续产生业务副作用”的结果，不声称撤销已经开始的执行。Dashboard 确认对话框列出 processing 是否包含在操作范围。

## 5. 总览统计与任务搜索

### 5.1 统计方案比较

| 方案 | 优点 | 代价与风险 |
|---|---|---|
| 每 5 秒扫描任务和历史 | 兼容旧数据 | 队列数量增长时成本按 `队列数 × 历史样本量` 增长；样本完成数不单调 |
| 状态转换累计指标 + 状态深度 | 读取量稳定，吞吐差值正确 | 浏览中的历史条数与累计完成数要分开命名 |
| 每次维护生成快照 | Dashboard 快 | 快照滞后，维护不可用时无新数据 |

总览采用状态转换累计指标：`completed_total` 等是单调计数，`history` 是当前 Redis 可读记录数。队列名优先来自注册表，旧数据的全键空间发现每小时最多执行一次。Worker 列表优先读取每队列索引，旧 Worker 的发现也按小时缓存。`retry_wait` 是 `delay` 的子集，剩余量只计 `ready + processing + legacy retry + delay`。前端速率对 `completed_total` 差值采样，计数重置时清空窗口。

对于当前仍未开始的执行截止任务，维护每队列 deadline ZSET；入队/重放写入，开始执行、终态取消或失败时删除，自动重试排队时重新写入。总览通过 `ZCOUNT` 读取当前逾期数。`retry_wait` 维护独立 gauge，并在到期迁移、管理移动和取消时同步更新。旧队列在暂停读写的维护窗口执行 `qtask rebuild-observation <queue>` 一次性回填；未回填时总览显示标记，避免把不完整指标当作精确值。

### 5.2 搜索方案比较

| 方案 | 优点 | 代价与风险 |
|---|---|---|
| 各队列先取 `limit` 再过滤 | 快 | 稀疏匹配和后续队列会被静默漏掉 |
| 任意 JSON 字段全量索引 | 查询快 | 写入成本和存储体积大；任意 substring 仍难支持 |
| 有边界的游标扫描 + 明确续页 | 兼容现有数据，完整遍历可得全部结果 | 稀疏查询需要多页；前端需展示“继续搜索” |

采用游标扫描。精确 task_id 直接访问任务 Hash；其余查询从各队列历史创建索引按 `created_at` 和 `task_id` 合并，再过滤并分页。游标保存每队列已读位置和查询起始时刻，新投递任务不插入已开始的遍历；历史记录过期仍可能使位置移动，调用方应按 task_id 去重。每次响应给出 `next_cursor`/`has_more`，扫描上限达到时明确告知，不把部分结果伪装成全集。`all` 包含 operational 和 Redis 中仍可读的终态历史；归档 SQLite 与外存正文不在该搜索范围。

## 6. 公开 API

`start_dashboard()` 通过当前包路径启动 `qtask_list.dashboard.main:app`；保持简单调用路径，同时把可选依赖缺失转为可理解的错误。`enqueue_many()` 明确承诺逐项提交、可能部分成功；发生异常时用 `BatchEnqueueError.results` 提供已完成的前缀。

## 7. 三轮查漏补缺

1. **正常路径**：入队、延迟、执行、完成、历史与外存回收的对象所有权可追踪；总览指标有互斥口径。
2. **故障与并发**：慢归档不阻塞心跳；待执行 claim 续租；失败入队不误删共享对象；GC 网络失败重试；重放创建新对象。
3. **兼容与控制面**：旧 V1/共享外存可读但不会被新清理路径误删；活跃任务删除有明确边界；搜索达到扫描上限时显式标示；公开启动入口按当前目录运行。
