# PLAN-021：PLAN-020 复查问题修复与循环评审

- 日期：2026-09-29
- 设计：`docs/design/qtask-review-remediation-20260929-overview.md`
- 范围：上轮评审确认的四个代码问题，以及六条失败测试所暴露的验证基线缺口。

## 实施步骤

1. 修复 Worker 停机竞态：drain 全程维持心跳；用短临界区串行化 handler 开始准入与 stop 信号，保留启动前收到的停止请求；尚未准入 handler 的 claim 原子退回 ready，恢复尝试预算、deadline 索引和租约；覆盖单线程、线程池等待和停机期间阻塞领取。
2. 将外存待入队回收改成 Redis 原子 pending→GC 转移，再执行可重试文件删除；手动删除也先撤销 pending 并保留 GC 日志，验证文件删除与日志更新之间退出时不能入队悬空引用。
3. 固定跨队列搜索的游标队列快照；保持显式队列筛选校验；队列详情的稀疏筛选改成有扫描上限和续页的 API/前端交互；约束 SDK 列表接口的扫描量。
   复查期间补充：彻底删除队列后同时失效旧队列发现缓存，避免 UI 保留幽灵队列。
4. 更新失效的 Dashboard 和外存测试断言，补充上述四项的针对性回归测试；同步 README 与项目使用指南的停机、扫描上限、游标和外存回收说明；在隔离 Redis 上运行全量测试，并运行 ruff、mypy、前端构建与 diff 检查。
5. 阅读本轮改动并重复修复、测试与复查，直至未发现未解决的本轮问题。记录结果到 `PLAN-021-review-followup-OUTCOME.md`，追加 `docs/dev/INDEX.md`，中文提交并立即推送。

## 验收

- 停机后不启动新 handler；已在执行的 handler 退出前不丢心跳或租约；退回任务不消耗 attempt。
- 外存文件在 pending GC 崩溃窗口中不会被 Redis 接受为新任务，删除失败会重试。
- 新建队列不打断跨队列搜索的旧游标；稀疏筛选单请求不超过扫描上限。
- 全量自动化测试通过；测试仅连接独立临时 Redis，不清理已有 6379/0 数据。
