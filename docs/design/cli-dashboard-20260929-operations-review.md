# CLI 与 Dashboard 真实场景评审

- 日期：2026-09-29
- 对象：`qtask_list/cli/__main__.py`、`qtask_list/dashboard/main.py`、`qtask_list/frontend/src/`
- 用户：多 namespace、30～100+ 队列的任务队列管理员与开发者
- 证据：当前源码、`qtask --help`、`QueueAdmin` 状态字段、已有设计与测试；`docs/HANDOFF.md` 关于“尚未实施 React”已过时，以 PLAN-017～021 和代码为准。

## 场景与结论

| 频率 | 场景 | 现有路径 | 评审结论 |
| --- | --- | --- | --- |
| 高频 | 值班时跨 namespace 看积压、死信、过期与失联 | Dashboard 总览；`qtask status` | Web 有分组；CLI 全局表遗漏 retry_wait、deadline_missed、Worker，`--namespace` 对全局表无效，也无 JSON/异常筛选，需补。 |
| 高频 | 某队列无完成，判断是停滞、无 Worker 还是仅等延迟 | Web 速率与“停滞”；队列诊断 | 浏览器打开后两个样本就可把健康队列判为停滞；仅有 delay 的队列也被判停滞。需观测时间门槛和状态区分。 |
| 高频 | ready 有任务但没有在线 Worker | 总览异常、队列诊断 | 总览会标异常，告警中心却不会提示；应新增“无人消费”告警，仅针对 ready，不对纯延迟队列告警。 |
| 高频 | DLQ 出现后定位任务、看错误并单条重放 | 告警→队列详情→任务抽屉 | 基本闭环存在；需要保留单条优先、批量二次确认。 |
| 中高 | 从 100 条队列中查近一天某 action 的任务 | `/tasks`、`/api/tasks` | 后端有 action 与游标，但全局页面没有时间/action 筛选；直接 `fetch` 绕过统一鉴权错误处理。需补。 |
| 中 | 恢复失联任务、清空或删除后核对结果 | 队列/Worker 页操作 | 操作后的全局数据 `reload()` 无效，页面可能继续显示旧状态直到轮询。需主动刷新。 |
| 中 | 管理员从队列详情手工投递 | “投递测试任务”主按钮 | 实际会执行真实 handler；默认示例缺 action，且重复抑制返回 `accepted=false` 时弹窗仍关闭。需改为次级操作、明确副作用并展示未投递原因。 |
| 中 | Redis 断线、认证过期时确认监控是否可信 | 顶栏/告警/总览 | `/api/health` 返回 `status=error` 被显示为“等待”；首次查询失败会呈现 0 或“没有告警”。需显示不可判定并重试。 |
| 中 | 自动化脚本巡检、一次性导出异常队列 | `qtask status` | 只能读富文本，无法可靠机器处理。补 `--json` 和异常筛选，保留原表格兼容。 |
| 低 | 新管理员查命令与处理原则 | `/guide`、README | 教程已有；Worker 空态示例含不存在的 `--queues`，需修正文案。 |
| 中 | 从 CLI 启动业务 Worker 并确认配置生效 | `qtask worker --module` | `--queue/--workers/--redis` 等参数目前不生效或只触发报错，却暴露在帮助中；入口应只接受业务模块，实际配置由模块内 Worker 实例决定。 |
| 低但高风险 | 为团队开放 Dashboard 远程访问 | `qtask dashboard --host 0.0.0.0` | 当前可无密码绑定所有网卡，页面含删除/重放操作；远程无认证必须显式确认意图。 |

## 用户接口方案比较

### 全局巡检 CLI

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 新增 `inspect` 命令 | 可独立设计输出 | 用户需记第二套巡检命令，与 `status` 重复。 |
| 扩展 `status`：`--namespace`、`--problems-only`、`--json` | 高频入口不变，表格与脚本共用一份快照 | 表格列变宽，必须控制列数。 |
| 只增强 `watch` | 适合交互盯盘 | 脚本与一次性检查仍无解。 |

采用扩展 `status`。JSON 输出为当前 `QueueAdmin.list_queues()` 原始行，避免丢字段；问题筛选口径固定为 DLQ/过期/失联，或 ready 有积压且无在线 Worker。指定单队列沿用详情表，但支持 JSON；`--namespace` 对全局表按 `ns:` 前缀筛选。

Worker 启动入口比较：保留无效的通用 `--queue` 参数兼容帮助会继续误导；让 CLI 从路径动态加载 handler 又会建立第二套注册协议；仅保留必填 `--module` 与现有示例一致，且业务 Worker 的 Redis/并发/队列配置只有一处来源。采用最后一种，未知旧参数由 Typer 明确拒绝。

远程 Dashboard 比较：一律禁止非 loopback 会挡住已有内网使用；只打印警告在自动部署日志中易被忽略；非 loopback 无认证时要求 `--allow-unauthenticated` 显式标记危险意图，默认本地用法不变。采用最后一种，并保留密码/认证配置的远程路径。

### Dashboard 盯盘口径

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 继续显示“完成/1h、进度百分比、停滞” | 改动少 | 浏览器打开不足 1h 时是错误时间口径；无期望总量时百分比不代表批次进度。 |
| 只显示可证实的“当前待处理、打开以来完成、采样速率、估计 ETA” | 数据来源清楚；无额外存储 | 无法给出本轮绝对完成百分比。 |
| 新增“本轮期望量”持久化模型 | 可算绝对进度 | 需定义调度轮次、跨 Worker 更新及何时重置，现有队列模型无法安全推断。 |

采用第二种。进度条若继续出现须显式标为“本次观测完成/当前待处理参考比”，不称批次进度；速率需至少两个不同时间的样本。`stalled` 仅对 ready 积压、在线 Worker 存在且持续观测至少 2 分钟无完成成立；无 Worker 是独立诊断，延迟等待不算停滞。第三种作为后续集成点，必须先从调度器提供轮次与期望量。

### 跨队列任务排查

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 维持自由文本搜索 | 简单 | 100 队列稀疏搜索需要大量分页，无法用时间缩小范围。 |
| 在既有全局 `/api/tasks` 增加时间参数并使用 action 精确筛选 | 复用 `search_tasks_page` 游标和扫描预算 | 输入项增加，需保留最短路径。 |
| 新建搜索索引 | 大规模查询更快 | 增加写路径和迁移成本。 |

采用第二种：默认仅显示搜索框和状态，展开高级筛选后才显示 action 与时间范围；统一 API 错误处理。保留扫描预算和“继续搜索”提示。

## 三轮查漏补缺

1. **正常路径**：CLI 默认表格与已有命令兼容；Web 单队列与跨队列查找都可下钻；操作后应看到新状态，且默认不改变危险操作确认方式。
2. **故障路径**：Redis 故障、API 4xx/5xx、登录过期、首次加载失败时不显示虚假的健康结论；旧样本在刷新失败后应明确标记过时；游标筛选变化后重新开始搜索。
3. **边界与性能**：100+ 队列不对每队列做历史扫描；状态异常筛选只依赖现有 `list_queues()` 行；无在线 Worker 与纯延迟队列区分；浏览器内采样不声称是服务端 1h 统计；`--json` 不混入富文本。

任务详情的“开始执行”和“完成”节点只采用 `last_started_at`/`started_at` 与 `finished_at`；旧记录缺字段时退化为“记录更新时间”。`deadline_missed` 是待处理消息的派生视图，不是终态，必须用 `/api/queue/{name}/requeue-expired` 更新截止并重放，不能当作普通终态直接调用 `replay_task`。
新截止时间必须晚于当前时间；服务端应在取消旧任务前验证，避免输入错误造成仍然过期的新任务。
分页搜索在筛选 `deadline_missed` 时需要将行的展示状态标记为 `deadline_missed`，同时保留真实 `location`；否则任务抽屉只看到 `ready`，过期重放入口无法出现。

## 页面结构与状态

沿用当前总览/队列/任务/Worker/告警/教程结构和双主题 tokens。总览首屏仍以队列矩阵和异常为主；增加采样口径说明。全局任务页把低频条件收在高级筛选。顶栏显示连接状态、最近成功刷新时刻和手动刷新。首次失败页显示“数据不可用”，不能显示 0 或“没有告警”；已有缓存时显示数据已过时。现有 tokens 与视觉布局可复用，无需另建视觉体系。

总览矩阵需有列名，避免多个无标签数字被误读；队列详情的手工投递移入“操作”，任务筛选保持主视觉层级。投递表单要求明确 action，并对重复抑制等 `accepted=false` 返回显示原因、保持弹窗打开。

## 不在本次直接推断的功能

- 本轮绝对进度：需要调度器提供 `run_id` 与 expected count，不能从累计完成数和当前剩余量推出。
- 多人共享的告警确认与 RBAC：现有 localStorage/单用户会话不足以定义协作责任；需要产品权限与确认语义。
- 精确最近一小时吞吐和失败率：需要服务端按完成时间的聚合指标；当前累计失败率告警应明确标为累计口径，不能写成“最近 50 条”。
