# 页面设计：总览（进度总览 Overview）

- 路由：`/` · 服务场景：S1 巡检 + S0 盯盘（几十到上百条抓取队列同时运行时的进度汇总）· 频率：高
- 信息优先级：P1 = 总体进度（活跃队列/总剩余/合计速率/异常队列）+ 异常队列行；P2 = 告警摘要；P3 = 空闲队列（折叠收纳）

## 面向"多 namespace、几十到上百个抓取任务"的适配

一个抓取任务类型 = 一个队列（`ns:queue_name`）。盯盘的核心问题是：
**每个队列完成了多少、还剩多少、按当前速率预计多久完成、哪些停滞/异常了。**

### 进度口径 `[假设，待与调度器口径对齐]`

| 概念 | 定义 | 数据来源 |
|---|---|---|
| 剩余 remaining | ready + processing + retry_wait + delay | `queue_stats`（现有） |
| 完成/1h | 最近 1 小时进入 completed 的任务数 | history 采样（现有） |
| 速率 | 前端每 5s 采样"完成数差值"估算（条/min） | 前端聚合 `[API 缺口，见 states.md]` |
| ETA | 剩余 / 速率；速率=0 且剩余>0 判定"停滞" | 前端计算 |
| 本轮期望总量 | 周期性调度（如 5min slot 全 universe）的"应完成总数"，作为百分比分母 | **开放问题**：需要调度器/期望清单提供，V1 先用"完成/1h vs 剩余"的相对进度示意 |

> V1 进度百分比 = 最近 1h 完成 / (最近 1h 完成 + 剩余)，是**吞吐视角的相对进度**，
> 不是"本轮应完成"的绝对进度；若后续接入期望清单（如 reconciler 的 JSONL 总量或
> scheduler 每轮 universe 大小），分母可切换为期望总量，展示"完成/期望"。

## 布局

```
┌──────────────────────────────────────────────────────────────────┐
│ KPI 行: 活跃队列 9/12 · 总剩余 16,342 · 合计速率 145 条/min · 异常 3 │  ← P1
├──────────────────────────────────────────────────────────────────┤
│ 告警摘要（最新 5 条 · 定位）                                       │  ← P2
├──────────────────────────────────────────────────────────────────┤
│ 队列进度矩阵（按 namespace 分组折叠）        [全部|进行中|仅异常]     │
│ ┌ ▾ backfill · 4 个队列 · 剩余 15,325 · 完成/1h 5,510 · ⚠1 ─────┐ │  ← P3 分组汇总行（可折叠）
│ │ bf:tick:2024H1  ▓▓▓░░ 58%   440   610  10.2  约43min  DLQ 3   │ │
│ │ bf:kline:2023   ▓░░░░ 20%   8,638 2,200 37   约3.9h   进行中  │ │
│ └──────────────────────────────────────────────────────────────┘ │
│ ┌ ▸ news · 2 个队列 · 剩余 0（整组空闲默认折叠）────────────────┐ │
│ ┌ ▾ stockev · 6 个队列 · 剩余 1,017 · 完成/1h 3,186 · ⚠2 ──────┐ │
│ │ stockev:universe:am ▓░░ 4%  500  20   -     停滞 ⚠           │ │  ← 异常行置顶
│ │ stockev:quote:5min  ▓▓▓░ 73% 266  720 12    约22min   DLQ 1  │ │
│ └──────────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────┘
```

- 列 = 队列 / 进度条 / 剩余 / 完成·1h / 速率 / 预计完成 / 状态。
- 进度条三段式：绿=最近 1h 完成，蓝=剩余（ready+processing+retry_wait+delay），红=DLQ。
- namespace 分组行是**汇总行**：组内队列数、总剩余、总完成/1h、异常数；点击折叠/展开。
- 默认排序：异常优先（DLQ/停滞/失败率），其次剩余量降序；整组空闲默认折叠。
- 筛选：全部 / 进行中（剩余>0）/ 仅异常；超过 ~50 个队列时建议只看进行中。

## 组件

- `<HealthSummaryCard>`：活跃队列 X/Y、总剩余、合计速率、异常队列。非 0 异常红色描边。
  **KPI 卡可下钻** `[v1.1 新增]`：

  | KPI | 点击下钻 |
  |---|---|
  | 活跃队列 | 队列列表页（预置"进行中"筛选） |
  | 总剩余 | 队列列表页（预置"进行中"筛选） |
  | 合计速率 | 不可点（无对应详情页），hover 提示采样口径 |
  | 异常队列 | 同页进度矩阵切"仅异常"并滚动定位 |

  可点击的 KPI 卡 hover 主色描边 + "点击查看…→"提示行；与"每屏主行动点唯一"不冲突——下钻是导航入口而非 CTA。
- `<AlertDigest>`：告警 Top5 + 定位 + "查看全部 →"。
- `<QueueHealthMatrix>`（改名"队列进度矩阵"）：
  - `<GroupHeaderRow>`：namespace 汇总 + 折叠开关
  - `<QueueProgressRow>`：`<ProgressBar>`（三段式）+ 计数 + ETA + `<Badge>` 状态
  - ETA 着色：正常=次要文字，停滞=danger
- 行点击 → 队列详情（URL 预置 `?state=…` 的定位能力保留）。

## 主行动点

无强 CTA（状态确认型页面）。矩阵行、组头、告警定位是主要交互。

## 状态

- 首次加载：KPI 与矩阵骨架屏。
- Redis 不可达：顶部错误条 + 矩阵置灰。
- 无队列：引导卡"用 `qtask push` 或在队列页投递第一条任务"。
- 极端规模（100+ 队列）：namespace 分组折叠 + "进行中"筛选；全展开超过 ~200 行时接虚拟滚动（实现注意项）。
- 速率采样冷启动（刚打开页面无差值）：显示"—"，两个采样周期（~10s）后出现。
